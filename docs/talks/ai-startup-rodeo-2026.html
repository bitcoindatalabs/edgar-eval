How we closed the gap

The model decides. Code does the rest.

1Parse the tables

Read straight from the filing’s HTML, every row with its page.

2Pick by line item

Revenue, cost of revenue, cash… one fixed list, no per-filing config.

3List every blank

“Not disclosed” becomes a lookup, not a guess.

4Code does the math

The model writes (1250 − 400) / 1250 × 100; code computes it.

5Code checks the answer

Inputs and quote must be in the context, the period must match. Else one retry.

6Search prose smarter

Short passages and stemmed keywords for risk and governance facts.

~13k tokens per question instead of 300k–460k

"None of these is clever alone. Together they turn 'read 400 pages' into 'look up a cited row'."

Row 1 (techniques 1–3) shrinks the filing to what questions need. Tables are chosen by a fixed list of standard line items, so nothing is tuned to my questions.

Click. Row 2: the model writes the arithmetic, code computes it. Code checks every input and the quote appear in the context and the period matches; a failed answer goes back once with the reason. Technique 6 handles prose questions.

What each bought us: 1–2 fixed the gross-margin misses; 4 removes rounding; 5's retry fixed four malformed answers on new filings; 6 found the Claude Code incident on p. 45.

Fair question

“Isn’t this just tool calling?”

A frontier agent with tools

The model decides when to search, what to compute, whether to check. Every step is a judgment call, at frontier prices.

Our workflow

The steps are fixed in code: extract, look up, compute, verify. The model fills narrow slots in one call. A 27B model can do that reliably.

Same ingredients. The difference is who owns the workflow, and that we measured it on filings we never tuned on.

Say yes first: "Yes, in spirit. Code execution and retrieval are tools, and frontier agents use them too."

"The difference: an agent decides its own plan, which takes a big model. We decide the plan once, in code, so a small model only has to look up and decide. And checking isn't optional: code verifies every answer."

"A frontier model with these tools would also do well, but you'd still pay frontier prices and send the filing out. The point is that the workflow, not the model size, carries the task."

Limits

Where this stops working

Extraction depends on document layout

Page splitting worked on all 24 S-1s we sampled from the 8 largest filing agents. Tables still need work on some small-company layouts; transcripts and contracts need new extractors.

Parity on factual, cited questions

Not open-ended analysis or judgment calls.

Four S-1s; easier held-out questions

Keyword search scored 91–93% there, and we haven’t tried embedding search yet. Harder sets and 10-Ks next.

“Local” ran through an API

Same open weights; not yet measured on a 24GB card.

30 seconds; it makes the parity claim stronger. The real limitation is the first card: techniques 1–3 depend on document layout, techniques 4–6 (code does the math, code checks, retry) carry over to anything.

If asked about coverage: by count, most 2024–25 S-1s come from small-company filing services, not Workiva or Donnelley. The page splitter handled all 24 sampled S-1s across the 8 largest agents. On the 12 where it found statement tables, every value checked out on 7 and the built-in check flagged the other 5. The remaining 12 had no full financial statements to parse, mostly SPACs and resale registrations.

What’s next

Can an LLM design the scaffolding for us?

→

Freeze, test held-out

A frontier model designs the workflow

Reads the failures, proposes a technique, writes it as code. Once per task.

A local model runs it

On every new document, at local cost, with code checking each answer.

The goal isn’t a smarter small model. It’s parity on a task, by design.

"I ran this loop by hand. Every step can be handed to an LLM: a frontier model is a good workflow designer, and the local model runs the result on every document."

"People already automate parts of this, like prompt and program optimizers such as DSPy. What finance needs on top is an eval you can trust, plus a held-out test, so an automated loop can't fool itself."

Three things to take home

1

Small models fail by omission

Keyword search said “not in the filing” 27 of 33 times. Give the model the right table and it answers.

2

Workflow beats size on narrow tasks

Code prepares, the model decides, code checks: a 27B model matched the frontier at 1/50th of the cost.

3

Prove it on documents you didn’t tune on

Freeze the code, then test held-out. That’s what makes 100% believable.
